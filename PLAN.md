# Plan: ClaudeDeck — Фаза 0, скелет и мониторинг сессий

<!-- 19 шагов: 1–8 разведка, 9–13 сквозной скелет, 14–19 мониторинг сессий. -->  

## Goal

Довести проект от пустого каталога до работающего read-only монитора сессий Claude Code на Stream Deck + XL: клавиши показывают состояние каждой сессии и заполненность контекста, включая сессии внутри WSL2. Попутно — снять все допущения, на которых стоят последующие фазы (usage и approve/deny).

## Assumptions / context

- Дизайн: [docs/design.md](docs/design.md). Этот план реализует Фазы 0–2 оттуда.
- Claude Code 2.1.232: на Windows (`~/.claude`) и отдельная копия в WSL Ubuntu-24.04 (`/home/gyv/.claude`). Второй дистрибутив Ubuntu-20.04 тоже запущен.
- .NET SDK 10.0.302. Тесты — xUnit, рендер клавиш — SkiaSharp.
- Репозиторий не инициализирован, рабочее дерево содержит только `docs/design.md`. Репозиторий будет **публичным** с первого коммита — отсюда требования к обезличиванию артефактов разведки и раннее CI.
- Стиль коммитов — по скиллу `commit-message` этого проекта: повелительное наклонение с префиксом подсистемы (`agent: ...`, `plugin: ...`).
- Хуки для разведки регистрируются в **проектном** `.claude/settings.json` внутри репозитория, а не в глобальном конфиге — эксперименты не должны задевать рабочие сессии в других каталогах.
- Отклонение от дизайна на время Фаз 0–2: локальный канал «хук → агент» делается по loopback HTTP, а не через unix-сокет/named pipe. `curl` есть и в Windows, и в WSL, контракт хуков (JSON в stdin, JSON в stdout) ложится на него напрямую. NativeAOT-shim из §3.2 дизайна вводится в Фазе 5, когда появится измеримая нагрузка.

## Risks

- **Формат payload'ов хуков не совпадает с предположениями §4.1.** → Разрешается Шагом 2.
- **`PreToolUse` может не давать реального контроля над разрешениями.** Вся Фаза 4 стоит на этом. → Разрешается Шагом 3.
- **Выбранная библиотека Stream Deck может не знать про 6 энкодеров нового устройства.** → Разрешается Шагом 4; при провале переходим на сырой WebSocket-протокол Elgato, объём — около дня.
- **Транспорт WSL → Windows может не завестись в конфигурации пользователя.** → Разрешается Шагом 5.
- **Серверный источник данных `/usage` может оказаться недоступен.** Это gate-решение для Фазы 3, не для этого плана. → Исследуется Шагом 6; при отрицательном результате Фаза 3 переходит в вид §5.3 дизайна (абсолютные числа без процентов) — решение принимает пользователь.
- **Реплика правил `permissions` может оказаться объёмнее, чем кажется.** → Объём оценивается Шагом 7. Риск ограничен по построению: обе возможные ошибки предсказания безопасны (§6.3 дизайна).
- **Определение PID процесса сессии через цепочку родителей может не работать.** → Проявится на Шаге 18; fallback по таймауту неактивности реализуется в том же шаге, поэтому шаг завершается успешно в любом случае.
- **Публичность репозитория превращает артефакты разведки в риск утечки.** Шаги 2, 6, 7 и 14 работают с реальными путями, конфигами, транскриптами и OAuth-токеном. → Обезличивание встроено в условия приёмки этих шагов, `.gitignore` закрывает секреты на Шаге 1.

## Steps

### Step 1: Инициализировать публичный репозиторий

- **Change:** `git init`, `.gitignore` для .NET с отдельным блоком на секреты (`.credentials.json`, `*.token`, сырые транскрипты), LICENSE, заготовка README, первый коммит с дизайн-документом. Репозиторий публичный с первого коммита, поэтому гигиена задаётся сразу, а не доводится в Фазе 6.
- **Files:** `.gitignore`, `LICENSE`, `README.md`, `docs/design.md`
- **Verify:** `git log --oneline` показывает один коммит; `git status` чист; `.gitignore` покрывает `**/.credentials.json` и `**/*.jsonl` вне `tests/fixtures/`
- **Commit:** `repo: initialize public repository with design document`

### Step 2: Записать реальные payload'ы хуков

- **Change:** Проектный `.claude/settings.json` регистрирует все хуки на скрипт-рекордер, который дописывает полученный JSON в `docs/findings/hooks/<event>.jsonl` и завершается с кодом 0, ничего не решая. Прогнать сессию в этом каталоге, задев все события. Результат — зафиксированная в репозитории фактура вместо предположений. Коммитятся **обезличенные** образцы: пути, имена пользователя и содержимое команд заменены плейсхолдерами.
- **Files:** `.claude/settings.json`, `tools/spike/capture-hook.ps1`, `tools/spike/sanitize.ps1`, `docs/findings/hooks/*.jsonl`
- **Verify:** есть записи для `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Notification`, `Stop`, `SessionEnd`; в них присутствуют `session_id`, `transcript_path`, `cwd`, `tool_name`, `tool_input`; отдельно проверить, приходит ли текущий режим permissions (от этого зависит точность §6.3). `Notification` придётся вызвать намеренно — запросом разрешения и простоем более минуты. Отдельная проверка перед коммитом: `git grep` по имени пользователя и по путям `D:\RSI` в `docs/findings/` не даёт совпадений.
- **Commit:** `spike: capture real hook payloads from Claude Code 2.1.232`

### Step 3: Проверить, что `PreToolUse` действительно решает

- **Change:** Скрипт-заглушка возвращает `deny` для конкретной безобидной команды, затем `allow`, затем `ask`. Наблюдаемое поведение записывается в findings. Это подтверждение или опровержение фундамента Фазы 4.
- **Files:** `tools/spike/decide-hook.ps1`, `docs/findings/pretooluse.md`
- **Verify:** при `deny` команда не выполняется и причина видна модели; при `allow` штатный промпт не показывается; при `ask` промпт показывается как обычно
- **Commit:** `spike: confirm PreToolUse permission decisions take effect`

### Step 4: Поднять минимальный плагин на живом устройстве

- **Change:** Манифест плагина и одно действие: клавиша со статическим текстом плюс энкодер с текстом на тач-полосе. Цель — проверить, что выбранная библиотека понимает Stream Deck + XL и все 6 энкодеров.
- **Files:** `com.gyaltchik.claudedeck.sdPlugin/manifest.json`, `src/ClaudeDeck.Plugin/*`, `docs/findings/streamdeck.md`
- **Verify:** плагин виден в Stream Deck, клавиша и энкодер отрисовываются на устройстве; в findings зафиксировано, доступны ли все 6 энкодеров и работает ли тач-полоса
- **Commit:** `plugin: add minimal action to validate Stream Deck + XL support`

### Step 5: Проверить транспорт WSL → Windows

- **Change:** Скрипт поднимает слушателя на Windows, из обоих дистрибутивов проверяется доступность. Фиксируется рабочий режим (mirrored или NAT), адрес хоста и нужные настройки файрвола.
- **Files:** `tools/spike/check-wsl-transport.ps1`, `docs/findings/wsl-transport.md`
- **Verify:** запрос из Ubuntu-24.04 и из Ubuntu-20.04 получает ответ от слушателя на Windows; в findings записан способ, которым это достигнуто
- **Commit:** `spike: verify WSL2 to Windows host transport`

### Step 6: Расследовать источник данных `/usage`

- **Change:** Определить, откуда клиент берёт цифры для `/usage` — перехват трафика CLI либо анализ бандла. Задокументировать эндпоинт, заголовки и форму ответа, либо обоснованно зафиксировать, что источник не найден.
- **Files:** `docs/findings/usage-source.md`
- **Verify:** findings содержит либо воспроизводимый способ получить те же проценты и время сброса, что показывает `/usage`, либо вывод «не найден» с описанием проверенного. Это gate-решение для Фазы 3. **В публичный репозиторий не попадают** ни токен, ни его фрагменты, ни сырые дампы трафика — только описание формы запроса и ответа.
- **Commit:** `spike: investigate usage data source behind /usage`

### Step 16: Отрисовать слот сессии на клавише

- **Change:** Действие `claudedeck.session`: цвет по состоянию, кольцо по заполненности контекста, подпись «проект / ветка». Слоты динамические, но **закреплённые**: сессия занимает наименьший свободный слот при первом появлении и удерживает его до завершения. Переупорядочивания по активности нет — иначе клавиши прыгают под пальцами, а на Фазе 4 та же клавиша будет разрешать команды. Освободившийся слот переиспользуется только новой сессией.
- **Files:** `src/ClaudeDeck.Plugin/*`, `com.gyaltchik.claudedeck.sdPlugin/*`
- **Verify:** на устройстве две параллельные сессии (одна на Windows, одна в WSL) занимают разные слоты и независимо меняют цвет и кольцо; при активной работе в одной из них позиции обеих остаются неизменными; после завершения сессии её слот освобождается и достаётся следующей новой
- **Commit:** `plugin: render session slot with state colour and context ring`

### Step 18: Определять мёртвые сессии

- **Change:** Захват PID процесса сессии по цепочке родителей на `SessionStart` плюс контроль mtime транскрипта; переход в `Stale`. Fallback по таймауту неактивности реализуется сразу, поэтому шаг закрывается даже если определение PID окажется ненадёжным.
- **Files:** `src/ClaudeDeck.Agent/*`, `tests/ClaudeDeck.Agent.Tests/*`
- **Verify:** закрыть терминал, не завершая сессию корректно — слот переходит в `Stale` в пределах заданного таймаута; в тестах покрыт путь без определённого PID
- **Commit:** `agent: mark sessions stale when the process is gone`

### Step 19: Подсвечивать сессии, требующие внимания

- **Change:** Слот мигает при переходе в `NeedsAttention` или `WaitingInput`, плюс клавиша глобального мьюта алертов. Замыкает Фазу 2: продукт становится пригодным для повседневного использования.
- **Files:** `src/ClaudeDeck.Plugin/*`, `com.gyaltchik.claudedeck.sdPlugin/manifest.json`
- **Verify:** на устройстве сессия, ждущая ответа, начинает мигать; мьют гасит подсветку и не влияет на сами состояния
- **Commit:** `plugin: alert on sessions needing attention`

## Дальнейшие фазы (детализация после Шага 8)

Разбивка на атомарные шаги для них преждевременна — она зависит от результатов разведки.

- **Фаза 3 — Usage.** `IUsageProvider` поверх источника, найденного Шагом 6; клавиши и энкодеры 5ч/неделя с процентом и временем сброса; опрос с бэкоффом; честное «нет данных» при недоступности. Форма фазы определяется gate-решением Шага 6.
- **Фаза 4 — Approve/Deny.** Матчер правил `permissions` (§6.3), три варианта ответа с паритетом консоли (§6.2), стор правил «Allow always» с возможностью отзыва, классификация опасности, длинное нажатие, правила безопасности §6.4. Объём матчера уточняется Шагом 7.
- **Фаза 5 — WSL и удалёнка.** Транспорты по итогам Шага 5, NativeAOT hook shim вместо `curl`, `claudedeck agent install` с автопатчем `settings.json`, задел под SSH-туннель.
- **Фаза 6 — Упаковка.** Property Inspector, готовый профиль для Stream Deck + XL, сборка `.streamDeckPlugin` в релиз из CI, README со скриншотами, инструкция по установке агента.

## Out of scope

- Approve/Deny в любом виде — до Фазы 4 плагин не принимает решений и не вмешивается в работу сессий. Хуки в Фазах 0–2 всегда возвращают управление без решения (кроме изолированного Шага 3).
- Отображение usage — до Фазы 3.
- Удалённые машины по SSH — задел в протоколе, реализация после v1.
- Отправка промптов в сессию, фокус окна сессии, стоимость — v2.
- macOS и Linux в роли хоста плагина.
